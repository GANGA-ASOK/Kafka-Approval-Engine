# Frontend assumptions & decisions

## Stack & build
- Tailwind v4 now runs through the `@tailwindcss/vite` plugin, with `@import "tailwindcss"` in `src/index.css`. The v3 leftovers (`tailwind.config.js`, `@tailwind` directives, autoprefixer and postcss deps) and the Vite boilerplate (`App.css`, `src/assets/*`, `public/icons.svg`) were removed.
- Design tokens are CSS variables on `:root`, overridden by `.dark` and exposed to Tailwind with `@theme inline` (`bg-canvas`, `text-ink`, `bg-ok-soft`, `text-role-finance` …). Dark mode is class-based. It follows the OS by default; the Light/Dark/System switch in the sidebar stores the choice in `localStorage` under `relay.theme`. An inline script in `index.html` applies the theme before first paint to avoid a flash.
- Added deps: `@tanstack/react-query` (fetching, polling, cache), `sonner` (toasts), `date-fns`, `@fontsource-variable/instrument-sans` and `@fontsource-variable/jetbrains-mono` (fonts are self-hosted, so the app needs no external CDN in Docker), and the dev dep `@tailwindcss/vite`.
- Admin pages are lazy-loaded routes. React and router code go in a `react` chunk and other `node_modules` in a `vendor` chunk (`build.rolldownOptions.output.codeSplitting`). No chunk exceeds 500 kB.
- Routing uses `createBrowserRouter` (a data router) so the workflow editor can use `useBlocker` for its "unsaved changes" guard.

## API integration
- Base URL is `VITE_API_URL` (default `http://localhost:8000/api`); see `.env.example`.
- Health is read from `<API origin>/health` and falls back to `<VITE_API_URL>/health`, or uses `VITE_HEALTH_URL` if set. It is polled every 15 s. The sidebar shows Mongo, Redis and Kafka dots, plus a Workers dot when the backend sends the additive `workers` field.
- The JWT and the cached user are kept in `localStorage` (`relay.token`, `relay.user`). On load, `/auth/me` refreshes the profile. A 401 on any call except `/auth/login` clears the session and redirects to `/login?next=…` with an "expired" toast. A failed login (401) shows an inline error on the form.
- Responses are normalised so `_id` becomes `id` if the backend ever sends `_id`. List endpoints accept either `{items,total}` or a bare array.
- Errors: `detail` string → shown verbatim. `detail` list (raw FastAPI 422) → joined as "field: msg". Network errors name the API URL so developers know what to start.
- `POST /requests` sends an `Idempotency-Key` that is generated once per form instance (`crypto.randomUUID`), so double-submits and retries reuse it.
- **202 handling:** after approve, reject or cancel, the request id enters a small in-memory "pending" store (`lib/processing.ts`). Every screen showing that request displays "Processing…". The store polls `GET /requests/{id}` every 1.2 s until `version`, `status` or `current_step` changes, then updates the cache, invalidates lists, stats and the timeline, and shows a toast naming the outcome ("Approved. … moved on to Finance"). It stops after 30 s with an informational toast.
- Auto-refresh: request detail every 1.5 s while `SUBMITTED` and every 5 s while active, stopping when the request is final. The timeline refetches whenever the request `version` changes. Lists refresh every 10 s, stats every 15 s, and the DLQ every 10 s. The audit "Live tail" refreshes every 3 s, jumps to page 1, and briefly highlights new rows.

## UX decisions
- Permission hints mirror the backend so the UI never offers an action that will 403: you can't decide your own request, you must be the step's *current* `assigned_role` (so escalated steps go to the escalation target) or ADMIN, and the request can't be final or still routing. The server remains the authority, and its error is shown if it disagrees.
- The cancel button shows for the requester and for ADMIN (the backend allows both) while the request is not final.
- Request type options: Purchase, Travel, Software, Training and Other, plus any `request_type` that has a workflow. Types without a workflow fall back to the default purchase workflow on the server. Department is free text with suggestions and defaults to the user's department.
- The "description" field is required in the UI (at least 5 characters) even though the API defaults it to `""`, because approvers need context.
- SLA chip: green, then amber in the last 25% of the step window (or the final minute), then red "Overdue by …" once past due. An escalated step keeps `breached=true` with a new deadline, so its colour follows the new deadline. The "Escalated to X" note on the step shows the breach history.
- Audit summary chips count event types **on the current page** (the API has no aggregate endpoint) and are labelled that way. Chips toggle a multi-select filter, sent as comma-separated `event_type`, which the backend supports. The Event dropdown is single-select. Dates are local calendar days, converted to ISO `from` (start of day) and `to` (end of day). Filters live in the URL, so a filtered view can be shared or bookmarked. CSV export covers the current page only, as specified.
- The workflow editor sends the full workflow (name, request_type, active, rules with `priority` = list order, escalation) on `PUT`, even though the backend accepts partial updates. `request_type` is read-only for existing workflows. Delete is hidden for `WF-DEFAULT-PURCHASE` (the backend returns 409). Client-side validation: names required and unique, min ≥ 0, max > min, at least one step, SLA hours > 0 and ≤ 90 days, and no role escalating to itself. A "Try a request" panel runs the contract's matching algorithm on unsaved edits.
- DLQ: defaults to the `PENDING` ("Needs attention") filter, and "All" omits the `status` param. Replay and discard confirm first. The empty state explains how to trigger a dead letter with `[fail]`.
- The Users page filters by role and search on the client (the endpoint isn't paginated). "Add user" can generate a temporary password.
- Visual identity: a navy "rail" sidebar with an amber active marker. The recurring motif is the transit-style **route line** (stations = approval steps) used on the login page, route preview, list mini-stepper and detail stepper. Fonts: Instrument Sans (UI) and JetBrains Mono, used only for machine identifiers (REQ ids, event ids, JSON). Copy is sentence case with plain-language status labels (`PENDING_APPROVAL` → "Awaiting approval", `SLA_BREACHED` → "Deadline missed").
- Accessibility: every field has a label, hints and errors are connected with `aria-describedby`, `aria-invalid` is set on invalid fields, focus rings are visible, there's a skip link, dialogs are native `<dialog>` (focus trap and Esc), segmented controls are radio groups, the live toggle is a `switch`, motion respects `prefers-reduced-motion`, and the layout has no horizontal scroll at 375 px (the audit table becomes a stacked list on mobile).
